# 一、统一 API 设计

原则：
**统一 REST 风格 + 所有写操作必须带 request_id + 所有异步操作返回 task_id + 所有错误走 error_code。**

你的原文档已经要求所有操作走 Task Engine、request_id 幂等、trace_id、ValidateNode、错误码统一，这里直接收敛成一套 API。

## 1. System API

```text
GET /api/v1/system/health
GET /api/v1/system/status
GET /api/v1/system/version
```

# 三、精确 Bulk Retry 规则

Bulk Retry 的核心不是“再跑一次”，而是：
**只重试失败项，不碰成功项，不重新解析已成功写入的数据。**

你的文档已经明确 Bulk retry 只能处理 failed 项，不能重跑成功项。 这里把它工程化。

## 1. Bulk Item 状态

```text
pending_scan
scanned
validation_success
validation_failed
ready_execute
executing
execute_success
execute_failed
retry_pending
retrying
retry_success
retry_failed
skipped
```

## 2. 哪些 item 可以 retry

只允许以下状态进入 retry：

```text
validation_failed
execute_failed
retry_failed
```

禁止 retry：

```text
execute_success
retry_success
skipped
```

## 3. Retry 输入

```json
{
  "request_id": "retry_bulk_20260429_001",
  "retry_mode": "failed_only",
  "max_retry": 3
}
```

## 4. Retry 查询规则

```sql
SELECT *
FROM bulk_items
WHERE bulk_job_id = :bulk_job_id
AND status IN ('validation_failed', 'execute_failed', 'retry_failed')
AND retry_count < 3;
```

## 5. Retry 不允许重新执行成功项

执行前必须检查：

```text
if item.status in execute_success / retry_success:
    skip
```

如果 Agent 重跑全部，直接判定失败。

## 6. Retry 必须重新校验失败项

原因：用户可能修复了文件。

流程：

```text
读取失败 bulk_item
↓
根据 source_file + source_line + source_hash 定位源数据
↓
重新 parse 当前文件
↓
重新计算 new_source_hash
↓
重新 validate
↓
validate 通过才 execute
```

## 7. source_hash 规则

每条 Bulk Item 必须生成：

```text
source_hash = sha256(site_id + item_type + source_file + source_line + normalized_content)
```

用途：

```text
判断是否同一条记录
判断用户是否修改过失败项
防止重复导入
防止 retry 找错对象
```

## 8. 如果用户修改了失败文件怎么办

```text
旧 source_hash != 新 source_hash
```

允许继续 retry，但要记录：

```text
details.changed_after_failure = true
details.old_source_hash = xxx
details.new_source_hash = xxx
```

## 9. Retry 成功后如何更新 report

```text
原 failed_items - retry_success_count
success_items + retry_success_count
retry_count + 1
```

但不能覆盖历史错误，必须保留历史。

## 10. Retry 失败如何处理

```text
retry_count + 1
status = retry_failed
记录新的 bulk_errors
保留旧错误
```

## 11. Retry 触发 deploy 规则

```text
如果 retry_success_count > 0:
    触发 Publish → Render → Deploy

如果 retry_success_count = 0:
    不触发 deploy
```

## 12. Retry 最终流程

```text
POST /api/v1/bulk/jobs/{bulk_job_id}/retry-failed
↓
Task Engine 创建 retry_bulk task
↓
Lock site_id
↓
查询 failed items
↓
逐条重新 parse
↓
重新 validate
↓
只 execute validate 通过的失败项
↓
成功项不碰
↓
失败项记录 error
↓
有成功变更才 deploy
↓
生成 retry report
↓
释放锁
```

# 四、告诉 Agent 增加 Deploy 快照结构的话

你可以直接复制下面这段给 Agent：

```text
你必须为 Site Factory OS 增加每次 deploy 的快照数据结构，作为部署回滚和审计的核心依据。

强制要求：

1. 每一次 deploy 都必须生成 deploy_id。
2. 每一次 deploy 都必须写入 deployments 表。
3. 每一次 deploy 都必须记录：
   - deploy_id
   - site_id
   - task_id
   - trace_id
   - request_id
   - deploy_type
   - status
   - repo_name
   - repo_branch
   - commit_id
   - previous_commit_id
   - manifest_hash
   - dist_path
   - live_url
   - created_by
   - created_at
   - finished_at

4. 每一次 deploy 都必须生成 deployment_files 明细，记录本次部署涉及的文件：
   - file_path
   - content_hash
   - file_size
   - action: added / modified / deleted / unchanged

5. deploy 前必须读取当前 repo 最新 commit_id，作为 previous_commit_id。
6. deploy 成功后必须保存新的 commit_id。
7. rollback 不允许凭空回滚，必须根据 deploy_id 找到 previous_commit_id。
8. rollback 本身也必须创建新的 deploy 记录，deploy_type = rollback。
9. rollback 成功后必须重新触发 GitHub Pages 部署检测。
10. DNS、Cloudflare Zone、NS 修改不允许自动回滚，只能记录并提示人工确认。

验收标准：

- POST /api/v1/sites/{site_id}/deployments 后，deployments 表必须新增记录。
- 每次部署必须能通过 GET /api/v1/sites/{site_id}/deployments 查看历史。
- POST /api/v1/deployments/{deploy_id}/rollback 必须能根据 previous_commit_id 回滚。
- 如果 deploy_id 不存在，返回 DEPLOY_ROLLBACK_FAILED。
- 如果 previous_commit_id 为空，禁止回滚并返回 DEPLOY_ROLLBACK_FAILED。
- 所有 deploy / rollback 必须写 task_logs、audit_logs、error_logs。
```

```text
你正在实现 Site Factory OS（SFS）终版系统。

总原则：
```
